# 输出内容规范管理 · 产品文档 v0.2

> **它是什么**：一套把「回复该长什么样」从口头偏好变成**机器可判、可退回、可记账、可自我进化**的机制。
> **给谁用**：长期靠大模型产出正式文档的人。它不提升模型能力，它拦住模型最容易犯、人又反复纠正的那几类毛病。
> **怎么读**：一等讲问题，二等列需求（带来源），三等是抽象模型，四等起是设计与差距。要动手改，看第九节和 `docs/design-language.md`。

---

## 一、问题域：六类失效

模型的毛病不是「不会写」，是**写了但读者要多花力气去核**。本仓库只治能被机器认出来的六类，其余归人。

| # | 失效 | 典型症状 | 读者的代价 | 机器怎么认 |
|---|---|---|---|---|
| F1 | 没调查就结论 | 「这个方案可行」但没查过平台支不支持 | 照着做才发现走不通 | 结论句无出处锚点、无实测痕迹 |
| F2 | 完成断言无证据 | 「已修好」「已对齐」「全部通过」 | 得自己重跑一遍才知道真假 | 完成类动词 + 本轮无可复核坐标 |
| F3 | 拿符号当解释 | 通篇脚本名、路径、退出码、函数名 | 每读三行要翻译一次 | 结论节技术符号密度超阈值 |
| F4 | 形状散架 | 结论埋在第三段；没有质检注脚；要点成一堵墙 | 扫三眼找不到答案 | 缺横幅／缺注脚／无粗体引导无表格 |
| F5 | 过程话当交付 | 「我先跑了个脚本」「定稿 hits 通过」 | 读到的全是动作，没有结论 | 过程播报短语、机器串混入正文与注脚 |
| F6 | 推回与绕过 | 「下一步要不要我…」「根因在工作区外」 | 活又回到自己手上 | 推回话术、过程性否定无替代路径 |

**为什么只选这六类**：它们都有客观判据（能写成正则或结构检查），且都出现在真实事故里。像「文风好不好」「有没有洞察」这类没有稳定判据的，写进规范但不进判据——**误报一多，闸就会被人关掉，等于没有**。

## 二、需求汇总（带来源）

来源代号：`原` ＝ 用户直接下的要求；`故` ＝ 会话中的真实事故；`抽` ＝ 由多起事故归纳出的条款。

| # | 需求 | 来源 | 状态 |
|---|---|---|---|
| R1 | 结论在第一行，读者扫三眼能点头 | 原 | 已实现（`缺正式回复横幅`＋结论节检查） |
| R2 | 每条结论要有本轮可复核证据 | 原 | 已实现（`完成类断言无本轮输出`） |
| R3 | 禁止「下一步／要不要我／等你确认／待办」收尾 | 原 | 已实现（`过程性否定未给替代路径`） |
| R4 | 用 3W5H 讲人话；技术符号只能当证据，且紧跟一句人话 | 原 | 已实现（`结论用日志搬运代替人话`） |
| R5 | 正式回复头部要有与正文区分开的横幅 | 原 | 已实现（`缺正式回复横幅`，引用块方案） |
| R6 | 注脚要有美学规范，不许丢 | 原 | 已实现（`缺质检注脚`／`注脚混入机器串`） |
| R7 | 正文分层：不同层级要有字号／粗细／图标区别度 | 原 | 部分（判据只查「一堵墙」与段落长度，三档视觉差靠规范约束） |
| R8 | 遇阻不许把「不在工作区」当结论，先报方案再解决 | 原 | 已实现（技能条款＋门禁人工项） |
| R9 | 说「已发布」必须区分「本地提交」与「已推送到远端」 | 故 | 已实现（`docs/release.md` 上线清单） |
| R10 | 开源包换机器必须真能跑，不许只在开发树里能跑 | 故 | 已实现（`tests/test_second_machine.py`＋`test_portable.py`） |
| R11 | 判据要能被确定性替身与真模型分别验收 | 抽 | 已实现（`test_loop.py` 替身闭环） |
| R12 | 通过／打回都要落账，供日后自学 | 抽 | 已实现（宿主侧台账，见第十节） |
| R13 | 新机制先答「现有能力为什么不扩」 | 抽 | 已实现（第九节＋技能治理条） |
| R14 | 数字要么带出处、要么带算式，不许编个像样的 | 故 | 已实现（`数字无依据或算式不复算`＋`judge/numcheck.py`） |
| R15 | 文档与实现不许漂移 | 故 | **本次补**（`tests/test_doc_truth.py`） |
| R16 | 遇阻先出方案报批，不许标注「做不到」收口 | 原 | 已实现（附录 B） |
| R17 | 结论必须是本轮实测或读到的整段事实，推断只许留在要点并标明 | 原 | **v0.3 补**（`结论含推断`，2026-11-19「禁止推断：必须实测」） |
| R18 | 横幅只盖最终那一份成稿，一篇回复只许出现一次 | 故 | **v0.3 补**（`横幅重复出现`，两份终稿并存的歧义） |

`故` 类都对应一处真实事故：R9 来自「把本地三条提交说成已发布」，R10 来自「换机器就报找不到文件」，R14 来自模型编了一个看着对的算式，R15 来自本文件自己把 17 条标签写成 12 条。

## 三、抽象模型

三层职责，五个事件，两个闭环。新增任何东西，先回答「属于哪一层的哪个事件」，否则不加。

```
         ┌────────────────── 三层 ──────────────────┐
         │ 口径层  规范正文（六项 + 主动姿态）        │ 人改，一处生效
         │ 形状层  横幅 / 结论 / 要点 / 注脚          │ 人改，一处生效
         │ 判据层  19 条标签 + 每条一句整改指令       │ 人改，两侧用例守
         └──────────────────────────────────────────┘
                        ▲ 读
   ┌──────────── 五个事件（宿主负责拉起）────────────┐
   │ ① 注入  每轮开始，贴骨架与近期高频毛病            │
   │ ② 审查  成稿前跑判据，返回命中与整改要求          │
   │ ③ 台账  每次通过／打回追加一行                   │
   │ ④ 退回  改过文件的回合，命中即当场重写            │
   │ ⑤ 巡检  每日自查：判据同源、台账是否停摆          │
   └─────────────────────────────────────────────────┘
                        ▼ 产出
   短闭环 A：命中 → 带整改要求重写 → 再判 → 放行
   长闭环 B：台账累积 → 每日提炼高频毛病 → 次日注入自查段
```

**两个闭环的分工**：A 管这一份稿子能不能交；B 管同类毛病下次还会不会犯。只有 A 没有 B，是死守规则不进步；只有 B 没有 A，是天天总结当场照犯。

## 四、判据体系

19 条标签，分三组。**每条必须带整改指令**——只报「错了」不告诉怎么改，等于把问题推回给人。

| 组 | 标签 | 治什么 |
|---|---|---|
| 证据组 | 完成类断言无本轮输出／未调查即结论／结论含推断／数字无依据或算式不复算／全量断言无清单／评分栏位未填 | F1 F2 R14 R17 |
| 人话组 | 结论用日志搬运代替人话／AI味套话／正文混入过程播报／用「必须知道的事实」类小节藏未完成项／敷衍占位 | F3 F5 |
| 形状组 | 缺正式回复横幅／横幅重复出现／缺质检注脚／注脚混入机器串／要点未分层／正文段落过长／机器横幅污染正文／落地未给回滚与灾备／指路式交付未自含／过程性否定未给替代路径 | F4 F6 R3 R18 |

**三条设计取舍**（都踩过坑）：

- **短回复豁免**：不足 400 字不查形状组。查了会逼人给一句话答复加横幅，反而烦。
- **「去 AI 味」只查固定短语**：三段式排比、破折号属判断项，写成正则会误伤正确写法。
- **只有一个阈值是真的**：段落 260 字——来自被认可成稿里最长段落 248 字。其余阈值宁可松，不误报。

## 五、交付契约（回复形状）

每份正式回复四段结构，**结论永远在最前**：

| 位置 | 内容 | 谁守 |
|---|---|---|
| 第 1 行 | `> ✅ **输出规范审查已通过，以下正式回复**`（全篇只许出现一次） | `缺正式回复横幅`／`横幅重复出现` |
| 结论 | `## 🎯 结论：<判断句>`，标题里不许只写「结论」 | 结论节检查 |
| 要点 | 每条粗体引导词或表格；单段 ≤260 字 | `要点未分层`／`正文段落过长` |
| 注脚 | `---` 空行 + `> **🔍 铁律质检**　通过（NN/100，置信度 0.NN）` + 一句人话 | `缺质检注脚`／`注脚混入机器串` |

**三档视觉差**（R7）：一级是标题（大、粗、独占一行、带图标），二级是要点行首粗体引导词，三级是普通解释句；三档不许用同一格式串行铺开。

**横幅为什么用引用块，不用图片或彩色块**：实测桌面端打包的渲染器把 `allowDangerousHtml` 关死、也不认 GitHub alert 语法，原始 HTML 与彩色块会原样露出标签；引用块在桌面端是加粗引用条、飞书企微是引用块、纯文本是 `> ✅` 开头一行——三处都不丢「已通过」。图片横幅在纯文本通道只剩一行路径。

## 六、部署形态

| 组成 | 在哪 | 作用 | 换宿主时 |
|---|---|---|---|
| 判据库 `judge/` | 本仓库 | 真值，唯一事实源 | 直接复用 |
| 口径与形状 `SKILL.md` | 本仓库根目录 | 人读的规范正文 | 直接复用 |
| 回归 `tests/` | 本仓库 | 改判据的刹车 | 直接复用 |
| 宿主适配（3 个文件） | 宿主插件目录 | 绑五个事件 | **需重写**，事件名各平台不同 |
| 台账与巡检产物 | 宿主数据目录 | 长期毛病统计 | 位置随宿主 |

**这条边界必须说清**：本仓库保证「判据与规范可搬」，不保证「事件绑定可搬」。把绑定塞进包里，等于把某个平台的 API 焊死在产品里，换平台即报废。够了的标准：适配层写满三个文件（注入、审查、事件注册），判据一行不改。

## 七、独立部署／独立管理／独立进化 的可执行定义

三个词都要能验收，不是口号：

| 能力 | 可执行定义 | 验收方式 |
|---|---|---|
| 独立部署 | 空目录 + Python 3.10+，不改全局配置，判据可用 | `test_second_machine.py`（剥光环境变量）+ 干净容器跑通 |
| 独立管理 | 改判据只动一个文件，改口径只动一个 md，改完有测试拦 | `test_reply_hits.py`（该拦/该放两侧）+ `test_doc_truth.py` |
| 独立进化 | 台账累积 → 提炼候选 → 人工裁决 → 进判据或规范 | 候选池不自动生效，每条候选带证据行号 |

## 九、怎么改它（给后来人）

1. **改口径**：只改 `SKILL.md` 的规范块，改完即生效（宿主按修改时间重读）。
2. **加判据**：只改 `judge/reply_rules.py`，必须同时补「该拦」与「该放」两侧用例；跑 `tests/test_reply_hits.py` 全绿才算加完。
3. **加事件**：只改宿主适配层，判据不动。
4. **改文档**：改完跑 `tests/test_doc_truth.py`——它会把「文档说的」和「代码做的」对一遍。
5. **发版**：按 `docs/release.md` 走，不许跳步。

## 十、宿主侧实况（本机 Hermes，供参考）

这一节不属于产品本体，是「在一个真实宿主上跑起来之后长什么样」，换宿主时整节作废。

| 项 | 实况 |
|---|---|
| 渠道覆盖 | 桌面／CLI、飞书、企微、定时任务车道，四条路走同一个审查入口；外部脚本走网关钩子 |
| 台账 | 每份成稿一行，含字数、模式、渠道、命中标签 |
| 每日沉淀 | 23:10 提炼高频毛病 → 次日注入「近期毛病·自查」段 |
| 每日巡检 | 08:20，正常时零输出，异常才报一行标题 |
| 提示词分级 | 首轮约 1400 字全文，之后约 350 字骨架，实测省 75% |
| 已知坑 | 插件只在进程启动时加载；改完不重启，台账里会看到「字数没变、新字段为空」——那是没生效，不是逻辑写错 |

## 十二、边界：它不做什么

- **不提能力**：不教模型写好文章，只拦它已经犯的错。
- **不做主观审美**：文风、洞察、结构精妙归人。
- **不查事实真假**：只查「有没有出处」，出处本身对不对要靠人。
- **不自动改规范**：候选只提案，进判据必须人裁决。
- **不管代码质量**：那部分在 `judge/codecheck.py`，八条可数判据，与本文件并行。

## 附录 A：术语

| 词 | 意思 |
|---|---|
| 标签 | 判据命中时返回的中文短名，如「缺正式回复横幅」 |
| 整改指令 | 每条标签附带的「该怎么改」一句话，供重写时照做 |
| 骨架 | 后续轮次下发的精简规范（约 350 字），首轮才发全文 |
| 台账 | 每次通过/打回追加的一行记录，供统计与提炼 |
| 替身 | 不带智能的确定性写作者，用来验收「整改指令是否可执行」 |

## 附录 B：两条流程铁律（从事故里长出来的）

- **遇阻不许绕**：门禁红项、依赖缺失、路径越界——「不在我管的地方」不是结论。三步：判归属 → 出迁移方案报批 → 批准后做完再报。
- **说「已发布」先分清三种状态**：本地提交／已推到远端／已在远端可见（带可打开的地址）。三者混说，就是把「能跑」说成「上线」。
