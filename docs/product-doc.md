# 输出内容规范管理 · 产品文档

> 一句话：一层管「怎么写」（正文）、一层管「合不合格」（判据）、一层管「谁来执行」（事件与定时任务）。
> 这份文档随实现同步更新——行为改了文档不改，就是误导后来人（规范第 6 条）。

## 一、它解决什么问题

模型写出来的东西有四个常见毛病：①没调查就下结论 ②说「做完了」但没证据 ③拿脚本路径当解释、人要翻译 ④客套废话多。
这套机制把四件事变成**机器可判**，并在每一份成稿上过一遍，不合格就退回重写。

## 二、架构（三层）

| 层 | 装什么 | 谁来维护 | 在哪 |
|---|---|---|---|
| 正文 | 六项规范 + 主动姿态 | 人（改一处，全渠道生效） | 技能 `output-standard` 的 `STANDARD` 块 |
| 形状 | 🎯/📌/自检注脚 | 人 | 技能 `reply-contract` 的 `TEMPLATE` 块 |
| 判据 | 21 条正则 + 12 个标签 → 整改指令 | 人 | `iron/reply_rules.py::review` |
| 执行 | 下发 / 退回 / 记账 / 网关收口 | 平台事件 + 定时任务 | 插件 `output-standard` + `iron-core` + `litellm-hooks/gw_standard.py` |

**三条硬约束**：正文只一处、判据只一处、每个职责只有一个执行体。

## 三、一次提问会发生什么

```
你开口 → 下发（全文首轮 / 骨架后续 + 高频毛病 + 上轮整改）
      → 模型出稿
      → 审查：通过就静默；不通过就记账并挂到下一轮
      → 改过文件的回合：收尾前还能当场退回重写（iron-core 独家）
```

## 四、覆盖哪些渠道（已实测）

| 渠道 | 走哪条路 | 有证据吗 |
|---|---|---|
| 桌面 / CLI | `finalize_turn` → `transform_llm_output` | 账本 `platform` 字段 |
| 飞书 | 同上（网关发消息也走 `run_conversation`） | `probe_channels.py` 11/11 |
| 企微 | 同上 | 同上 |
| cron 车道 | 同上 | 同上 |
| 外部脚本 / 其它 Agent | LiteLLM 网关钩子 | mark 模式实测 |

## 五、自学习闭环

| 环 | 谁在跑 | 节奏 | 产出 |
|---|---|---|---|
| 记账 | 插件 `transform_llm_output` | 每份成稿 | `iron/state/std-review.jsonl` |
| 沉淀 | `scripts/std_daily_learn.py` | 每日 23:10 | `std-lessons.json` + `std-learning.md` |
| 应用 | 插件 `pre_llm_call` | 每次提问 | 「近期高频毛病·自查」段 |

**边界**：候选只提案；偶发一次不念；测试只写测试账。

## 六、自动巡检

`scripts/std_patrol.py`，每日 08:20（cron `output-standard-patrol`），查五件事：判据同源（源/容器文件/进程内存）、自学习是否停摆、渠道是否偏斜、载体是否唯一、归档是否膨胀。
**正常时零输出**（不打扰），异常才报一行标题 + 若干条。

## 七、插件改动怎么生效（必须知道的坑）

Hermes 插件只在网关进程**启动时**加载。改完插件代码，旧进程里仍是旧实现——账本里会看到「字数没变、新字段全是 None」，那就是没生效，不是逻辑写错。

正确做法：改动后在有一次性令牌、且无活跃会话的窗口里重启网关。
`scripts/gateway_reload_when_idle.py` 是三守卫版本（幂等 / 单次令牌 / 无活跃会话），
**但它不能挂 cron**：平台明确禁止 cron 驱动网关生命周期（防 SIGTERM-respawn 循环，平台错误信息原文如此）。
所以它是「人触发、机器把关」的脚本：人建令牌 → 跑脚本 → 脚本自己判能不能动。

2026-11-19 实测：重启前账本 `chars=1912 / mode=None / platform=None`，重启后 `chars=1688 / mode=full+budget / platform=cli`，
次轮 `chars=545 / mode=skeleton`，省 68%。

## 八、提示词分级（成本控制）

首轮全文（约 1400 字），之后每轮骨架（约 350 字）。实测省 75%，关键三样（骨架 / 高频毛病 / 整改要求）一个不少。
为什么这么做：判据审的是成稿，重复贴全文换不来遵守。

## 九、门禁

| 编号 | 查什么 | 失效后果 |
|---|---|---|
| G46 | 正文唯一 + 自学习不停摆 + 标签稳定 | 下发与审查各判一套 / 自学习悄悄停了 |
| G47 | 判据同源（源 / 容器文件 / 进程内存三份哈希）+ 导出齐备 | 桌面拦、网关放 / 加了判据网关拿不到 |
| G51 | 载体唯一 | 副本满天飞，改一处不生效 |
| G53 | 差距分析（原始要求逐条有可复核证据） | 只答最新追问，原始任务被跳过 |
| G55 | 代码质量八条（形容词→数字：行数/函数/重复/依赖/吞错/路径/说明/来源） | 「说优化了但没优化」没人拦，只能反复追问 |

## 九·六、代码怎么写（可执行，不靠自觉）

「优雅、简练、稳健、一看就懂」是形容词，形容词没法验收——于是每轮都能说「做了」。
这份规范把它们换成能数的东西，八条判据见技能 `software-development/code-quality-standard`，
验收由 `iron/codecheck.py` 执行，门禁 `G55` 守着。

| 编号 | 查什么 | 阈值 |
|---|---|---|
| C1 | 单文件规模 | >600 提醒，>900 失败 |
| C2 | 标了可移植的文件不许依赖平台 | 零 |
| C3 | 同一常量只许定义一处 | 1 处 |
| C4 | 不许裸 except 吞错 | 0 |
| C5 | 单函数长度 | >60 提醒，>100 失败 |
| C6 | 公开函数必须有说明 | 全部 |
| C7 | 不许写死家目录路径 | 0 |
| C8 | 连续 8 行重复 | 0 处 |

## 九·五、数字怎么算才可信

模型错数字不是态度问题，是能力问题：它模仿数字的形状，不做真实运算。所以光要求「给计算说明」不够——它照样能编一个看着对的算式。

三类分开治：

| 数字类型 | 要求 | 谁把关 |
|---|---|---|
| 引用型（别人的数据） | 带可复核出处（文件:行号 / 命令输出 / 账本行） | 判据查锚点在不在 |
| 计算型（自己算的） | 写成 `=算式= 结果` | `iron/numcheck.py` 真复算，对不上判失败 |
| 估算型 | 明标「推断」并给区间 | 判据查有没有标 |

普通计数（「21 条要求」）不管：管太宽会天天误报，误报多了这条闸就被人关掉了，等于没有。

## 十、怎么改它（给后来人）

1. **改口径**：只改技能里的 `STANDARD` 块，改完立刻生效（插件按 mtime 重读）。别在插件里抄一份。
2. **加判据**：只改 `iron/reply_rules.py`（判据只此一处），补「该拦 / 该放」两侧用例（LX67），然后 `python litellm-hooks/build_rules.py` 重导出，最后重挂网关。**别写回 `iron_hook.py`**——那是平台钩子，只管什么时候调；写回去门禁 G47 会拦。
3. **加事件**：只改 `plugins/output-standard/__init__.py`（平台差异都在这层）；`standard.py` 与判据不动。
4. **改预算**：只改 `inject.py` 的 `BUDGET_RATIO`／`CHARS_PER_TOKEN`；预算是按窗口比例算的，不是写死的字数。

## 十一、已知边界（不掩盖）

- 纯问答回合没有同轮退回原语，最强保证是「下一轮带着账重写」。要真正同轮只能改内核，违反升级免疫。
- 「去 AI 味」机器只查四类固定短语；三段式、破折号属判断项，写成正则会误伤正确风格。
- 目前只在本机 Hermes 真跑过；换平台只需重写 `__init__.py` 的事件绑定，`standard.py` 可复用。
- 数字闸只能保证「算术对」「出处指得到」，不能保证「那个出处本身是对的」——最后一层要靠人。
- 网关侧只查「数字有没有交代」，不做复算（容器里没有复算器）；真复算在桌面端。
