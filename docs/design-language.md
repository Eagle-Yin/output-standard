# 设计语言 · 文字与代码同一套标准

> 这份文件定义两件事：**读者看到的文字长什么样**，和**维护者写的代码长什么样**。
> 两者不是两套标准——都只服务一个目的：**让下一个接手的人少花力气**。

---

## 一、语言原则（写给人看的部分）

| # | 原则 | 做法 | 反例 |
|---|---|---|---|
| L1 | 结论先行 | 第一句就是答案：行不行、改没改、选哪个 | 先讲背景三段，答案在末尾 |
| L2 | 人话优先 | 技术符号只能当证据，且紧跟一句解释它意味着什么 | 「`exit=1`，`G47` 失败」← 读者不知道后果 |
| L3 | 一句一事 | 一条要点出现两个「并且」就拆成两条 | 一条要点塞进三层因果 |
| L4 | 数字三型 | 引用型带出处、计算型带算式、估算型标「推断」 | 「命中 47 条」← 47 从哪来 |
| L5 | 不推回 | 能判断的自己判断；需要授权的说明「需要什么、为什么只能你给」 | 「下一步要不要我…」 |
| L6 | 说完成带痕迹 | 说「修好了」必须同句给出本轮可核对的坐标 | 「已全部验证通过」 |
| L7 | 三种状态分开说 | 本地改完／已推送／远端可见，不许合成一句「已发布」 | 「已上线」其实只在本地 |

## 二、视觉语法（排版层级）

**三档视觉差**，一眼能分出「哪句是判断、哪句是依据、哪句是注解」：

| 档 | 用途 | 形式 |
|---|---|---|
| 一级 | 结论 | `## 🎯 结论：<判断句>`，大字、加粗、独占一行、带图标 |
| 二级 | 要点 | 行首粗体引导词（`- **是什么**：…`，引导词不超过八字），或用表格 |
| 三级 | 解释／代价 | 普通正文句，只用来补一句为什么 |

**四条排版规则**：

- **能上表格不写三段话**：对比、清单、取舍一律表格——表格自带层级。
- **单段 ≤260 字**：超了就拆。这个数来自被认可成稿里最长段落 248 字。
- **图标只在锚点用**：🎯📌🔍⚠ 各司其职，不撒装饰。正式坏消息零装饰。
- **注入节与正文分家**：开场横幅、结尾注脚与正文之间都有空行隔离，绝不混排。

**横幅**：正式回复第一行 `> ✅ **输出规范审查已通过，以下正式回复**`。
为什么不用图片或彩色块：渲染端实测把原始 HTML 关死、也不认 GitHub alert 语法，写进去就是标签原样露出；引用块在桌面端是加粗引用条、飞书企微是引用块、纯文本是 `> ✅` 开头一行，三处都不丢「已通过」。

**注脚**：`---` 独占一行 → 空行 → 引用块。首行固定
`> **🔍 铁律质检**　通过（NN/100，置信度 0.NN）`，其后一句人话写「凭什么站得住、代价是什么、哪块没验」。
注脚里不许出现 `hits []`、`exit=0`、`3558 字符` 这类机器串，更不许把注脚的格式说明当注脚写进去。

## 三、代码风格（写给维护者的部分）

**总则：像写句子一样写代码——一行做一件事，名字说人话，异常不吞。**

| # | 规则 | 验收方式 |
|---|---|---|
| C1 | 单文件 ≤600 行（>900 失败） | `judge/codecheck.py` |
| C2 | 标了可移植的文件零平台依赖 | 同上 |
| C3 | 同一常量只定义一处 | 同上 |
| C4 | 不许裸 `except:` 吞错 | 同上 |
| C5 | 单函数 ≤60 行（>100 失败） | 同上 |
| C6 | 公开函数必须有 docstring 说明「干什么、为什么」 | 同上 |
| C7 | 不许写死家目录路径 | 同上 |
| C8 | 连续 8 行重复即抽函数 | 同上 |

**追加五条（写作风格，不进自动判据，进 code review）**：

- **不引依赖**：标准库够用就用标准库。为几行代码加一个包，等于把升级风险转给每个使用者。
- **一个函数一件事**：函数名读起来像一句话（`claim_offenders(text)` 而不是 `check(text)`）。
- **错误要带上下文**：`raise SystemExit("判据库加载失败：%s" % path)`，不写 `raise`。
- **注释只写代码说不出的事**：为什么这么写、什么情况下要改；不写「这里判断是否为空」。
- **短路的限度要写下来**：`# shortcut: 只认中文，接英文语料前要重测` —— 一句注释，胜过日后一次事故。

## 四、文档风格

- **文档与实现同一次提交**：行为改了文档不改，就是误导后来人。`tests/test_doc_truth.py` 会拦明显漂移。
- **不写会过期的话**：不写「目前支持 21 条」，写「17 条（以 `judge/reply_rules.py` 实测为准）」。
- **每条边界都写**：不掩盖做不到的部分；承认边界比假装完整可信。
- **术语表必备**：读者不该为了看懂文档去读源码。

---

## 五、拒绝清单（这些不做）

- 不为了「看起来专业」引入术语堆砌。
- 不为了「功能丰富」加没人要的选项。
- 不为了「覆盖全面」写会误报的判据——**误报一次，闸就被关掉**。
- 不为了「显得忙」写过程播报。
- 不为了「以后可能用」预留抽象。
