# 代码质量规范

## When to Use

- 要新建、重构、大幅修改任何代码文件之前（先看规矩再动手）
- 交付代码前（跑检查，失败项清零）
- 有人问「这代码能开源吗 / 别人用得上吗」——先跑可移植性检查再回答

写代码时按这份规范做；交付前跑 `python iron/codecheck.py --all`，失败项清零才算完。

这份规范是**可执行的**：每条判据都有对应的机器检查（`iron/codecheck.py` 的 C1–C8），
不是靠自觉。规范与检查同源，改规范就改那一个文件，别在别处再抄一份。

## 为什么需要它

「优雅、简练、稳健、让人一看就懂」是形容词。形容词没法验收，于是每次都能说「做了」。
把它们拆成能数的东西之后，「做没做」就不再是争论：行数、函数长度、重复块、依赖方向，
查一遍就有答案。

## 八条判据

| 编号 | 判据 | 阈值 | 为什么 |
|---|---|---|---|
| C1 | 单文件规模 | ≤600 行提醒，>900 失败 | 一次读不完就没人读，改一处要滚很久，实测漏改过 |
| C2 | 标了可移植的文件不许依赖平台 | 零 | 承诺能拷走却 import 平台模块，等于没开源 |
| C3 | 同一常量只许定义一处 | 1 处 | 两处各判一套，改一边另一边不动 |
| C4 | 不许裸 except 吞错 | 0 | 出问题查不出哪一步挂的 |
| C5 | 单函数长度 | >60 提醒，>100 失败 | 一屏放不下，读的人会跳过 |
| C6 | 公开函数必须有说明 | 全部 | 「一看就懂」里能机器判定的那部分 |
| C7 | 不许写死家目录路径 | 0 | 换台机器一行都跑不动 |
| C8 | 连续 8 行重复 | 0 处 | 同一段逻辑抄两遍，改一处必漏一处 |

## 第一原则：形容词必须翻译成数字

「优雅、简练、稳健、让人一看就懂」是意图，不是标准。两边都用形容词，你说不像、我说像，永远收敛不了。**接到这类要求，先答一句「几天后你用什么数判断我做没做」，答不出来就先翻译，翻译完再动手。**（LX89）

## 写新代码时的四条硬规矩

1. **先问要不要写。** 能不写就不写：标准库、平台已有能力、现成依赖，按这个顺序找。
   自研之前必须书面回答「现有哪个能力不够、为什么不能扩它」。
2. **纯逻辑与平台代码分家。** 「什么算合格/正确」是纯逻辑，零依赖、能单文件拷走；
   「什么时候调用、从哪读配置」才是平台相关。混在一起，别人想用就得先剥掉全部平台代码，
   实际结果是没人用得上。
3. **注释只写「为什么」和「踩过什么坑」。** 不写「这里定义一个变量」这种代码本身能说的。
   每条反直觉的实现旁边留一句：「为什么这么写」＋「原来那样写错在哪」。
4. **改结构必须有三关验证。** 等价（改前改后逐条结论相同）、可移植（拷到空目录还能跑）、
   单一来源（别处再长一份会被拦）。凭「看着对」验收结构改动，是本项目踩过最多次的坑。

## 去 AI 味的具体做法

代码里的 AI 味比文字里更隐蔽，常见的四种：

- **过度防御**：每个参数都 isinstance 一遍、每步都 try/except 一遍。判据：防御代码超过业务代码，就是写多了。
- **抽象叠抽象**：为了「以后可能要用」抽一层，结果只有一处调用。判据：一层抽象只有一个调用方，删掉。
- **命名含糊**：`handle_data`、`process_item`、`do_work`。改成说清是什么的名字：`review`、`budget_chars`、`claim_offenders`。
- **注释复述代码**：`# 遍历列表` 写在 for 循环上。删掉，或者改成讲为什么这么做。

## 交付前必做

```
python iron/codecheck.py --all      # 失败项必须清零
python iron/test_rules_parity.py    # 动过判据才需要：等价性
python iron/test_rules_portable.py  # 声称可移植才需要：可移植性
```

提醒（warn）不算失败，但要在交付里说清还剩几处债、为什么不修。
